# 为什么叫「人类荣耀」

AI 替我们写完一个功能，代码进了仓库。过几天，另一个地方出了相似的问题，我们能不能自己认出来？

拿一个搜索框来说。用户先搜「苹果」，又改搜「梨」，屏幕上却偶尔跳回苹果。生产代码里，请求、缓存、页面生命周期和列表刷新搅在一起。要是从页面入口逐行往下读，可能看完几百行，仍然解释不了眼前的现象。两次搜索都成功了，怎么偏偏留下了用户已经换掉的那个词？

## 从生产代码里取出一个问题

把页面、服务器和列表都拿掉，只留下两次请求、一个显示结果的位置。先发 A，再发 B。我们可以自己决定谁先返回。这时才看得清楚，用户发起搜索的顺序和程序收到结果的顺序，是两回事。

这就是我们说的「原子知识」。一个语法、一条 API 约定、一段生命周期、一个并发条件，都可能成为一课。拆到多小，要看能不能保住原来的问题。如果把第二次请求也删了，程序会更短，可旧结果已经没有机会覆盖新结果了。一条值得留下的知识，既要说得出它在什么条件下成立，也要找得回生产代码里受它影响的那一行。

## 让实验有机会推翻解释

教这条知识时，先把问题交给学习者。A、B 依次发出，B、A 依次回来，每个回调都把自己的结果写到屏幕上。最后会看到谁？先猜，再跑。然后只改一处，让回调在写入前核对自己的请求编号，再跑一次。

如果两次都按 A、B 的顺序返回，两种写法都会留下 B，程序跑绿了也分不出这一行有什么用。换成 B、A 的返回顺序，普通写法留下 A，核对编号的写法留下 B。现在把判断删掉，旧结果就会再次出现。学习者可以换输入、改代码，让自己的解释接受检验。这也是我们坚持 Demo 必须真实可运行的原因。[运行搜索实验](../recipes/js-latest-request/README.md)

## 举一反三，也要知道哪里不同

过几天，播放器有了一个相似的毛病。用户已经从第一首歌切到第二首，第一首的封面才加载回来。学过搜索框的人，也许会先问「这张图回来时，屏幕上还是刚才那首歌吗？」能在另一个项目里提出这个问题，前面的搜索实验就值了。

再往前走一步。两个人同时打开同一篇笔记，各自修改后保存。旧草稿同样可能盖掉新内容，但这次两个编辑者各有进程，谁都看不到对方的请求编号。只在保存前查一次版本也不够，两个人可能都在对方写入前查到旧版本。把「版本仍然等于我打开时看到的值」写进数据库的更新条件，检查和写入才能在同一次更新中完成。前一课给了我们一个好问题，后一课要靠新的证据回答它。[运行双人编辑实验](../recipes/sql-version-guard/README.md)

## 学什么，由人作主

AI 每改一次代码都停下来讲课，开发就做不下去了。采集可以自动发生，学习的时机留给人。熟悉的知识再次出现，记下新的出处就可以略过。库里还没有、自己早就会的，一句「我会了」就够。今天只想弄懂搜索框，就挑这一条，其他的先放下。导入一个开源项目也是如此，可以带着自己的问题进去，只取值得研究的那一段。

时间久了，知识库里应当看得见同一个判断在哪里用过，又在哪里碰到了边界。树状目录方便找回它，同一条规律可以挂上几处源码。实验报告记录这次程序发生了什么，是否掌握由学习者自己决定。

这个插件做得好不好，可以等下次遇到问题时再看。有人说「切歌时封面偶尔会错」，你能在打开源码之前，先猜出一种会出错的顺序，再动手验证。那一刻，AI 写过的代码就成了你自己的经验。这份举一反三的本领，就是「人类荣耀」这个名字的来历。
